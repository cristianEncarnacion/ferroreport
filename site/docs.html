Documentation

ferroreport takes a template (JasperReports' .jrxml, or its own .ferro), your rows as JSON and your parameters, and returns a PDF, an Excel workbook, a Word document, a PowerPoint presentation, an OpenDocument file, a CSV file or an HTML preview. Every way of calling it, from the command line to Python, uses the same engine and produces the same bytes.

Your first PDF

You need three files: the template you designed in Jaspersoft Studio, the rows, and the parameters.

ferroreport render invoice.jrxml --data rows.json --params params.json -o invoice.pdf
# rows.json: one object per detail row; keys are the template's <field> names
[
  { "sku": "FX-1000", "description": "Hydraulic pump 2HP", "qty": 21, "price": "185.00" },
  { "sku": "FX-1007", "description": "Stainless steel valve", "qty": 26, "price": "42.50" }
]

# params.json: one key per <parameter>
{ "CUSTOMER": "Distribuidora Caribe, S.A.", "ISSUED": "2026-03-05", "TAX_RATE": "0.18" }

The same render from code:

// JavaScript
import { render } from "ferroreport";
const pdf = render(jrxml, rows, params, { locale: "es_DO" });

# Python
import ferroreport
pdf = ferroreport.render("invoice.jrxml", rows, params, locale="es_DO")

# Any language, over HTTP
curl -X POST localhost:8080/render/invoice -H 'Content-Type: application/json' \
  -d '{"data": [...], "params": {...}, "locale": "es_DO"}' -o invoice.pdf

Template, data, parameters

Template

The JRXML source, exactly as Jaspersoft Studio saves it (JRXML 6, and JRXML 7 as JasperReports 7 writes it), or a .ferro template: every function that takes a template takes either. Compiled .jasper files are never loaded: if a template names lines.jasper, ferroreport reads lines.jrxml (or lines.ferro) instead.

Data

A JSON array with one object per row, or one JSON object per line (JSON Lines). Keys match the <field name="..."> entries; a field named customer.name reads {"customer": {"name": ...}}. A missing key or null gives a null field. Each value is converted to the class the field declares:

Field classJSON you send
StringA string (other values are written as text)
Integer, Long, Double, FloatA number, or a numeric string
BigDecimalA number or a string. Use a string such as "185.00" to keep the exact digits
Booleantrue / false, or "true"
Date, Timestamp, TimeISO-8601 text ("2026-03-05", "2026-03-05T10:30:00", with or without offset) or epoch milliseconds
byte[] (images)Base64 text or a data: URI
List, CollectionA nested array, usually the rows of a subreport

Reports without a data source can omit the data. A template's SQL query runs on the database given with --db (see Rows from a database); without it, send the rows.

Rows from the libraries you read data with go in as they come, or with one call to make them plain values:

# pandas: hand over the DataFrame as JSON text. to_json writes NaN as null and dates as
# ISO-8601; to_dict("records") would keep NaN, which is not valid JSON.
pdf = ferroreport.render("orders.jrxml", df.to_json(orient="records", date_format="iso"))

# Polars: to_dicts() gives plain Python values (None for nulls, datetime.date for dates)
pdf = ferroreport.render("orders.jrxml", df.to_dicts())

# SQLAlchemy: rows as dicts; a generator is read one row at a time
from sqlalchemy import text

with engine.connect() as conn:
    result = conn.execute(text("select id, customer, placed, total from orders order by id"))
    pdf = ferroreport.render("orders.jrxml", (dict(row) for row in result.mappings()))

Parameters

A JSON object with one key per <parameter>, converted with the same rules. Parameters you leave out take their defaultValueExpression.

Templates in .ferro

.ferro is ferroreport's own template format: the same reports as JRXML, written as an indented outline instead of XML. It is about half the size, a person can write it without a designer, and its reports are accessible by default.

// Employees, with their salaries and the total.
report "Employees" lang=en
  style Base default fontName="DejaVu Sans" size=10
  field salary Double
  variable total Double calculation=Sum : {salary}

  title 40
    h1 0,0 555x30 size=18 : Employees
  columnHeader 20
    text 0,0 300x20 bold : Name
    text 300,0 255x20 bold align=right : Salary
  detail 20
    text 0,0 300x20 : {name}
    text 300,0 255x20 pattern=#,##0.00 align=right : {salary}
    image 0,0 20x20 alt="Photo of the employee" : {photo}
  summary 20
    text 300,0 255x20 bold align=right : Total: $V{total}

Texts and fields

A text is printed as written, unless it has holes: {name} (a field), $P{name}, $V{name} or $R{key} are filled in from the data.

WriteAnd you get
text : OverdueThe text, as it is. Braces that are not a name stay too: {0}, {a b}
text : Invoice {number} · {customer}The text with the values in it
text pattern=#,##0.00 : {total}The value alone, as a number (or date) that pattern= formats
text : ={qty} * {price}A text that starts with = is an expression, as in a spreadsheet
text : \{not a hole\} costs \$5\{, \}, \$, \= and \\ print the character itself

Fields need no declaration. A field written as {name} that has no field line is declared for you, in the report or in the each it is used in, with class Object: its values keep the type the data gives them (text, number, true or false, a list). Declare a field to give it a class: dates, which arrive as text, need field due Date before pattern= can format them, and JasperReports needs the class of a field used in arithmetic or in a condition to compile the JRXML. $F{name} still needs its declaration.

Accessible by default. A .ferro report gives a tagged PDF, the kind screen readers follow, unless it says tagged=false, in the language of lang= (or of the locale). h1 to h6 are headings (a static text tagged as one), alt="..." describes an image, and tag=th (or td, table, h2...) says what any element is.

Without coordinates

Positions and sizes can be left out, and ferroreport works them out:

report "Employees" lang=en
  field salary Double

  def money value
    text pattern=#,##0.00 align=right : {{value}}

  title gap=6
    h1 height=30 size=18 : Employees
    text height=14 color=gray : Everyone on the payroll
  detail
    row height=16
      text 3fr : {name}
      use money 1fr value={salary}
WriteAnd you get
Parts without x,yOne under the other, as wide as the band (or frame); the band is as tall as they need unless it gives a height
rowIts parts side by side. Each says its width: points (100), a share of the row (40%) or a fraction of what is left (2fr, 1fr; a part with no width is 1fr). height= sets the height of its parts
stackParts one under another inside a row
gap=On a band, frame, row or stack: the space between its parts, in points (4 unless you say)
def name params...A definition: the parts under it, with {{param}} where a value goes
use name param=valueThe definition's parts, with the values in place. A width (1fr) and other attributes on use go to its parts
if : {overdue}Its parts print only when the condition holds, and take no room when it does not (a frame with printWhenExpression and removeLineWhenBlank)
each : {lines}Its parts repeat for every row of a nested list; field lines inside it declare the rows' fields, when they need a class (a list component over a subdataset)
import "parts.ferro"Another file's definitions, styles and fields, from the template's folder or the resource folders

A part placed this way floats (it moves down when the one above it grows) and a text field grows with its text, so nothing overlaps when a value is longer than expected. Parts that give x,y stay where they say. convert writes the result as JRXML with every coordinate worked out, which Jaspersoft Studio and JasperReports open like any other report.

Everything JRXML 7 can say, .ferro can say, so converting between them loses nothing:

ferroreport convert invoice.jrxml -o invoice.ferro      # JRXML 6 or 7 -> .ferro
ferroreport convert invoice.ferro -o invoice.jrxml      # .ferro -> JRXML 7, for Jaspersoft Studio 7
ferroreport convert old.jrxml --to jrxml -o new.jrxml   # JRXML 6 -> JRXML 7

From code: convert(template, "ferro") in JavaScript, ferroreport.convert(template, to="ferro") in Python, ferroreport::template::from_jrxml, to_jrxml and ferroreport::convert::jrxml_to_v7 in Rust. Every fixture renders to the same pixels from its JRXML, its JRXML 7 and its .ferro.

The designer

The designer makes and changes templates in the browser, without writing them and without knowing JasperReports: the page in the middle, the fields of your data on the left, and what the selected part looks like on the right. It runs on your computer (the engine is WebAssembly), so neither the template nor the data leave it, and it keeps your work in the browser until you start a new report. It speaks English and Spanish (the EN / ES switch; at first, your browser's language), and the first time it opens it shows a three-step guide, which Help, Getting started shows again.

  1. Start from the invoice example, a blank report or a file (File, Open a file…: a .ferro or .jrxml; a .ferro that imports others opens when you select them together, and a JSON file selected with it becomes the data).
  2. Add your data: Upload data file, or Edit sample data (a list of rows in JSON). The designer lists its fields with their types in plain words (text, number, whole number, date, yes or no, list).
  3. Drag a field onto the page, or select an area and click the field. The areas have plain names: Report title (top of the first page), Top of every page, Column titles, Each row of your data (it repeats), Below the rows, Bottom of every page, End of the report (totals); their JasperReports names are in their tooltips. An empty area is a slim strip that says Add something here. A field dropped on the rows gets a column title above it; numbers are aligned right with a format; a list (an array in each row) becomes a part that repeats for each item, with its fields inside.
  4. Select a part to change it. Its Text box holds words and fields the way .ferro writes them, Invoice {number} · {customer}: type {, or press Insert a field, to choose one, and the page shows each field as a pill with its name. A text that is worked out with a formula (a method call, arithmetic, a condition) is shown under Advanced, as JasperReports writes it, and is saved as it was. The rest is in sections: Look (font, size, bold, italic, underline, colors), Alignment, Border, and, folded, Position and size and Advanced (grow to fit, blank when there is no value, show only when, the formula). Number formats are chosen by an example (1,234.56, $1,234.56, 12%, 2026-11-24). Ctrl+Z undoes; the arrow keys move.
  5. Download PDF (the main button), or Excel, Word or PowerPoint from its menu; the Preview tab shows the PDF, made again a moment after every change. File saves the template as .ferro or .jrxml (JasperReports 7). When the report cannot be made, a message over the page says why in plain words and what to do, with the engine's own message under Technical details.

Parts it cannot edit yet (charts, tables, crosstabs, subreports, barcodes) are shown as boxes and saved as they were. Images are kept inside the template as data: URIs, which ferroreport reads and JasperReports does not: give JasperReports the image as a file instead. A .ferro it saves has every position written out, as convert writes it, and imports and defs are expanded.

Editors can do the same from JavaScript: toTree(template) gives any template as a tree of its JRXML 7 form, and fromTree(tree, "ferro" | "jrxml") writes it back (see JavaScript).

doctor

Lists what a template uses and whether ferroreport can render it. Run it on a template before you rely on it. See Check a template.

convert

Rewrites a template: JRXML (6 or 7) as .ferro, .ferro as JRXML 7, or JRXML 6 as JRXML 7, the way JasperReports 7 writes its own samples. The output's extension, or --to ferro / --to jrxml, picks the format; without either, a JRXML becomes .ferro and a .ferro becomes JRXML. Without -o the result goes to standard output. Style templates (.jrtx) convert too.

migrate

Checks every template of a folder and its subfolders (.jrxml and .ferro) before you move to ferroreport: whether it loads, what it uses, what is not supported yet, and whether it renders with no rows (pictures are looked for next to each template, in its parent folder and in every --resources folder). It prints a line per template and a summary; --report migration.md (or .json) writes every template's result. With --to ferro --out converted/ (or --to jrxml, for JRXML 7) it also writes each template converted, in the same folders. It exits with 1 when a template cannot be loaded, so it can stop a build; with --strict also when one uses something not supported yet, stops when rendered with no rows, or differs from JasperReports. --strict-pixels (with --jasper) also fails it when a page of a template both engines render is a different picture, or when the pages could not be compared (no pdftoppm). A template one engine cannot render is left to --strict.

The migration guide takes a JasperReports project through it step by step.

Compared with JasperReports itself

With --jasper lib/, the folder of your JasperReports jars (6 or 7, with their dependencies, as your application runs them) and a JDK 11 or newer on the PATH, every template that loads is also rendered by JasperReports, in one Java process, and by ferroreport, from the same rows: <name>.json or data.json next to the template, and parameters from <name>.params.json or params.json (locale en_US, time zone UTC in both). For each it reports the pages of each, whether every text and number is the same and in the same place (their CSV exports, compared line by line), whether every page is the same picture, and how long each took to fill and write the PDF. The pictures are compared when pdftoppm (poppler) is on the PATH, as tools/compare.py compares them: at 100 DPI in gray, a page differs when more than 0.15% of its ink does; the worst page's share is given (and in the report, as worstPage and worstPageDiff). Without pdftoppm they are not compared, and the report says so. --keep compared/ keeps both PDFs and both CSVs of every template, and the diff picture of every page that differs (red: only JasperReports, blue: only ferroreport), to look at side by side. Images, styles and subreports are read from the template's folder; nothing is written there.

Errors come back as {"error": "what went wrong"} with one of these statuses: 400 the request is malformed, 401 the token is missing or wrong, 404 the template does not exist, 411 the request has no Content-Length and asks to switch protocols, 413 the body is too large or the render went over the page or time limit, 429 the client asked too often (--rate-limit), 422 the template or its data cannot be rendered, 507 the document is too large for the memory and disk the server may use (--spool-memory, --spool-dir, --spool-disk).

A document is sent only once it is complete, with its Content-Length: the answer is the whole document or an error, never part of one. It comes with two more headers: Server-Timing (milliseconds spent parsing the template, 0 when it came from the cache, and rendering) and X-Report-Pages.

Large reports over HTTP

Two things can be changed, each on its own, for reports with more rows than you want in memory.

Rows one per line. Send Content-Type: application/x-ndjson with the request (everything in the table above except data) on the first line, and one row per line after it. The server reads the rows as the report asks for them, so neither side holds them all: a million rows render with the server at about 50 MB. Send them straight from a query:

# rows.ndjson
{"params": {"YEAR": 2026}}
{"sku": "FX-1000", "qty": 21, "price": "185.00"}
{"sku": "FX-2000", "qty": 4, "price": "92.50"}

curl -X POST localhost:8080/render/sales -H 'Authorization: Bearer change-me' \
  -H 'Content-Type: application/x-ndjson' -T rows.ndjson -o sales.pdf

# or without a file, as the database produces them
psql -At -c "select row_to_json(s) from sales s" | { echo '{"params": {"YEAR": 2026}}'; cat; } | \
  curl -X POST localhost:8080/render/sales -H 'Authorization: Bearer change-me' \
    -H 'Content-Type: application/x-ndjson' -T - -o sales.pdf

The first line may be as large as --max-body; the rows have no limit of their own (--timeout, --max-pages and --max-rows are what stop a report that is too large).

The document as it renders. By default the server keeps the document until it is complete (in memory up to --spool-memory, then in a file), so that an error is always an error and never half a PDF. Add Prefer: respond-streaming and the document is sent while it renders instead: the first bytes arrive in a fraction of a second, however long the report is, and nothing is kept on the server. The answer says so with Preference-Applied: respond-streaming.

Images, subreports and style templates

A template refers to other files by relative path: "logo.png" in an image expression, "lines.jasper" in a subreport expression. ferroreport looks for them in the template's folder, then in the resource folders you add, then among the resources you pass in memory. A path can never leave those folders, and remote URLs are not fetched.

Images are PNG, JPEG or GIF (its first picture, with its transparent color). They can also come from the data: a byte[] field with base64 content, or a string field with a base64 expression.

A subreport gets its rows from a nested array in the parent row:

# Parent row
{ "order": "ORD-2026000", "customer": "Grupo Ramos",
  "lines": [ { "product": "Clavos 3\"", "qty": 26, "price": 65.0 }, ... ] }

# In the parent template: a field of class java.util.List, and
<dataSourceExpression><![CDATA[new JRMapCollectionDataSource($F{lines})]]></dataSourceExpression>
<subreportExpression><![CDATA["lines.jasper"]]></subreportExpression>    # read from lines.jrxml

JRBeanCollectionDataSource, ((JsonDataSource)$P{REPORT_DATA_SOURCE}).subDataSource("lines") and JREmptyDataSource work the same way. Subreport parameters and return values are supported.

Style templates are found the same way: <template><![CDATA["styles.jrtx"]]></template> reads styles.jrtx from the template's folder, a resource folder or the resources in memory (over HTTP, the resources of the request). A .jrtx that includes another is read with it, the included one looked for next to it first. Styles are taken in JasperReports' order: those of each template after the templates it includes, then the report's own; a style defined again replaces the earlier one for what comes after it. The location can be a string or a parameter whose default is one. In Rust, parse with Renderer::parse instead of ferroreport::parse, which does not read files.

Fields of the main report are not visible inside the table; pass them as parameters.

The rows come from the data source expression, or, when the dataset run passes $P{REPORT_CONNECTION}, from the subdataset's SQL query on the report's database.

Lists (jr:list) use the same datasetRun: the list contents are repeated for each row, one below the other, and continue on the next page when they do not fit.

Crosstabs

Crosstabs made in Jaspersoft Studio render as they do in JasperReports. The rows come from the report itself (place the crosstab in the summary band) or from a subdataset through its datasetRun, for example one crosstab per detail row over a nested JSON array.

  • Row and column groups sort their bucket values ascending or descending, and print their totals at the start, the end or not at all. Group headers sit at the start, middle or end of the cells they span (headerPosition).
  • Measures can be Sum, Count, DistinctCount, Average, Highest, Lowest, First or Nothing. In a cell, $V{measure} is the value of that cell, $V{measure_group_ALL} the total of a group, $V{measure_rowGroup_columnGroup_ALL} the total of both, and $V{group} the bucket value. Cells without data show zero for sums and counts. Totals add up the totals of the buckets below them, as Jasper does, so decimals round the same way.
  • A crosstab wider than its element is cut into column parts, printed one below the other (columnBreakOffset apart) with the row headers repeated. One taller than the page continues on the next page with the column headers repeated (repeatColumnHeaders, repeatRowHeaders).
  • <crosstabParameter> values are evaluated in the report and read with $P{} inside the crosstab.
  • percentageOf="GrandTotal" shows a measure as a percentage of the grand total (100 × value / total, in the measure's class: whole numbers divide as integers, BigDecimal rounds half up).
  • orderByExpression sorts a group's buckets by a value computed on each bucket's totals, for example $V{amountMeasure} to list regions by their sales; ties keep the natural order.

Not yet: bucket comparators (comparatorExpression), and crosstabs over the rows of a group only (they use all the rows read so far). ferroreport doctor warns about these.

Excel and CSV

A template that renders to PDF also exports to an Excel workbook (.xlsx) or a CSV file. Both follow JasperReports' own exporters with their default settings, so the spreadsheet comes out the way it did with Jasper: every fixture in the test suite gives the same worksheet, styles and CSV text as JasperReports 6.20, byte for byte.

Excel

  • All pages go on one sheet named after the report, one below the other, page margins included.
  • The edges of the elements cut each page into columns and rows. A column is as wide as the gap between two cuts (in Excel units of 6 points) and a row as tall as its gap, in points.
  • Each text sits in the cells it covers, merged, with its font, size, bold, italic, underline, color, background, borders and alignment. Rotated text is rotated in the cell. Styled and HTML text keeps its formatting run by run.
  • A text that does not fit its box is cut the same way as in the PDF.
  • Lines become the border of the cells they lie on, rectangles fill and outline their cells, and frames give their background and borders to the cells inside them.
  • Images sit over their cells with the same scale mode (RetainShape, FillFrame, Clip) and alignment. Charts and barcodes are drawn as pictures at twice Jasper's resolution, so they stay sharp.
  • Where two elements overlap, the one on top wins, as in Jasper; the other is left out.
  • Values are written as the text you see in the PDF (3,885.00), like Jasper. With --xlsx-numbers on the command line, or XlsxOptions { detect_cell_type: true } in Rust, numbers are written as numbers with their format pattern, so the spreadsheet can add them up.

CSV

Only texts are exported. Every line of a page where a text starts becomes a row, and every column where a text starts on that page becomes a field. Fields holding a comma, a quote or a line break are quoted; quotes are doubled. Pages follow one another.

A value that starts with =, +, - or @ can be run as a formula by the spreadsheet that opens the CSV. When the data comes from other people, turn on the guard (--csv-safe, csv_safe=True, csvSafe: true): those values get an apostrophe in front, which spreadsheets show as text. Numbers such as -12.50 are left alone. It is off by default so the CSV stays exactly what JasperReports writes.

Not available yet: the old XLS format and the net.sf.jasperreports.export.* properties other than number detection.

Word

Ask for docx (-o report.docx, format="docx", Format::Docx, Format.DOCX) and you get a Word document laid out like JasperReports' DOCX exporter: each page is a table cut at the edges of its elements, and each element sits in the cells it covers. Texts keep their fonts, sizes, colors, styled runs, alignment, padding, borders and backgrounds; images, charts and barcodes are pictures; lines and rectangles become cell borders and backgrounds. A page break separates the pages, so the document has as many pages as the PDF. Like Jasper's, the document is made for reading and light editing, not for reflowing: rounded rectangles and ellipses come out as plain boxes.

PowerPoint

Ask for pptx (-o report.pptx, format="pptx", Format::Pptx, Format.PPTX) and you get a presentation laid out like JasperReports' PPTX exporter: each page is a slide of the report's page size, and each element is a shape where it is on the page. Texts are text boxes with their fonts, sizes, bold, italic, underline, strike-through, colors, styled runs, alignment, padding, background, line spacing and rotation; rectangles (rounded too), ellipses and lines are shapes with their fill and pen; frames are rectangles under their elements; images are pictures cut to their element as in the PDF, and charts and barcodes are drawn as pictures. A box with the same border on every side gets it as the shape's outline, and borders that differ by side are drawn as lines (Jasper's exporter leaves those out). Links to web pages and other files work, and links to a page or an anchor of the report jump to its slide. Slides are written as the pages are filled.

Not available yet: the net.sf.jasperreports.export.pptx.* properties (such as a page used as the slide master) and fonts embedded in the file. PowerPoint and LibreOffice wrap text with their own font metrics, so a line that just fits in the PDF can wrap in the slide.

OpenDocument (ODS and ODT)

Ask for ods or odt (-o report.ods, format="odt", Format::Ods, Format.ODT) and you get the files LibreOffice and other OpenDocument applications open, laid out the way JasperReports' ODS and ODT exporters lay a report out. The spreadsheet is the Excel grid: every page on one sheet, the same columns, rows, merged cells, fonts, colors, borders, alignment and rotation, images over their cells, charts and barcodes as pictures. Values are text by default, like Jasper; with --xlsx-numbers numbers are numbers, with a number style made from their pattern (decimals, grouping, percent, scientific, text around them). The text document is the Word layout: a table per page, each element in the cells it covers, a page break between pages; ellipses and slanted lines are drawn as pictures. Links, anchors and page anchors carry over, and the page has the report's size.

Not available yet: the net.sf.jasperreports.export.ods.* and .odt.* properties, date cells for patterns with month or day names, AM/PM, two-digit years or milliseconds (they stay text), the per-mille sign in number styles, and upside-down text in ODT.

Large reports are written as they are made, in about the memory of a small one. A document's styles come before its body in the file, so a large report is filled once more first to find them (a spreadsheet three times in all: its columns, its styles, its rows; a text twice), and its rows are then compressed and written as they come: 100,000 rows in 69 MiB as ODS and 39 MiB as ODT, a million rows in 41 MiB as ODT. That needs rows that can be read again, as for large workbooks; rows that can only be read once still give the document, kept in memory until it is written.

Accessible PDFs

A PDF is a picture of pages unless it also says what is on them. With tagging on, the document carries that description (a tagged PDF): each text element is a paragraph and each image, chart and barcode a figure, in reading order; tables and crosstabs are tables, with their rows, their data cells and their header cells, each header saying whether it names a column or a row and each cell how many columns and rows it spans; the lists of an HTML text are lists, each item with its bullet or number and its body; lines, borders and backgrounds are marked as decoration, so a screen reader skips them; and the document has its title and the language of the locale. The pages look exactly the same.

PDF/A, attachments, signatures, encryption, links

PDF/A

For documents that must be kept for years (invoices, statements, records). --pdfa 2b (or 2u, 2a, 3b, 3u, 3a; pdfa in the packages and the HTTP API) writes PDF/A: every font inside the document, an sRGB output intent, the conformance declared in the metadata. Level a is also tagged. A text in one of the PDF standard fonts (a font no one provides) is an error, as in JasperReports: register the font with --font. The template's net.sf.jasperreports.export.pdfa.conformance property (pdfa2b...) asks for the same. Every fixture is checked with veraPDF as PDF/A-2a and PDF/A-3b on every push.

Attachments

--attach invoice.xml (or invoice.xml:application/xml) carries a file inside the PDF, the way electronic invoices carry their XML. PDF/A-3 allows any file; PDF/A-2 refuses them. In the packages: attachments, a list of paths or of (name, bytes, MIME type).

Links and bookmarks

Text fields, images and frames take JasperReports' hyperlinks: hyperlinkType Reference (a URL), LocalAnchor, LocalPage, RemoteAnchor and RemotePage, with hyperlinkReferenceExpression, hyperlinkAnchorExpression, hyperlinkPageExpression and hyperlinkTooltipExpression. anchorNameExpression names a place, and bookmarkLevel puts it in the PDF's outline (the bookmarks panel). HTML previews

Ask for html (-o report.html, format="html", Format::Html, Format.HTML) and you get one web page with every page of the report drawn as it is in the PDF: same positions, fonts, colors, images, charts and barcodes. The text is real text, so it can be selected, searched and read aloud, and everything from the template or the data is escaped. The page has no scripts and loads nothing from the network.

Each line of text carries its measured width, so the layout holds even where the browser does not have the report's font and falls back to another. Use it to show a report in a browser without a PDF viewer; the PDF remains the document to print or keep. In Rust, HtmlOptions { fragment: true, .. } gives only the pages, to place inside a page of your own.

Large reports and limits

A report does not have to fit in memory. Rows are read as the report asks for them and each page is written as soon as it is finished, so a million rows and 23,810 pages render in about 19 MB, at about 55,000 rows a second on one core.

What this covers, and what it does not:

  • PDF and CSV are written page by page. So are Excel workbooks, in two passes: the columns of a sheet come from every page, so a large report is filled once to find them and once more to write its rows, which are compressed and sent on as they are made (100,000 rows: about 4.5 s and 69 MiB; 500,000: 22 s and 103 MiB). That needs rows that can be read twice: a file, or rows the command line, the server, Python and Java put aside for you; in Rust, render_rows_to. Small workbooks are still filled once. A report with more rows than a sheet holds (1,048,576) stops with an error that says so. OpenDocument files are written as they are made too, filled once more first to find their styles (100,000 rows: 69 MiB as ODS, 39 MiB as ODT; a million rows as ODT: 41 MiB).
  • Values known only later, such as "page 3 of 240", a grand total in the title or a group total in the group header, are added to their page when they are known, without holding the page back. If something is drawn over such a value, its page waits for it instead, so the result is always the same document.
  • A crosstab over the report's own rows needs them all, so those rows are kept until the crosstab prints. Crosstabs, tables, lists and subreports over nested data are not affected.

Rows from a database

A template's own SQL query runs the way JasperReports runs it over JDBC: $P{} values are bound parameters, $P!{} is pasted into the SQL text, and $X{IN, column, PARAM} (with NOTIN, EQUAL, NOTEQUAL, LESS, LESS], GREATER, [GREATER and the BETWEEN forms) becomes its clause. Subreports, tables, lists, crosstabs and charts that pass $P{REPORT_CONNECTION} run their own query on the same database. Rows are read as the report needs them.

ferroreport render sales.jrxml --db mysql://reports@db:3306/erp -o sales.xlsx
ferroreport render sales.jrxml --db "jdbc:sqlserver://db:1433;databaseName=erp;user=reports" -o sales.pdf
ferroreport render sales.jrxml --db sqlite:app.db -o sales.pdf

Fonts

DejaVu Sans, DejaVu Serif and DejaVu Sans Mono are built in. They are the families of the jasperreports-fonts extension, so templates that use them match JasperReports exactly. A family the engine does not have is replaced by a built-in one.

Add your own TrueType or OpenType fonts with --font on the command line or register_font in Rust. The JavaScript and Python packages use the built-in families for now.

A JasperReports font extension is read where JasperReports would find it on its class path: in a resource folder (the template's folder or one given with -r) with a jasperreports_extension.properties at its root. render and check register the font families and font sets of the fonts.xml files it names (net.sf.jasperreports.extension.simple.font.families.*), with the font files at the paths the extension gives them, and warn about any they cannot read; in Rust, load_font_extensions does it for the renderer's resources. Extensions inside jars are not read: unpack the jar into a folder.

Bold or italic text in a family that has no face for that style is drawn from its regular face, and the PDF simulates the style as JasperReports does: bold by stroking the outlines as well, italic by slanting the text.

A character the text's font does not have is left out of the PDF, as JasperReports leaves it out (when the text is measured for its height it still counts as wide as the font's missing-glyph box, as in JasperReports). To draw it in another font, use a font set or font fallback:

  • Font sets work as the <fontSet> of a JasperReports font extension. With --font-set "Serif Fallback=DejaVu Serif,DejaVu Sans" (or register_font_set), a text whose font name is Serif Fallback is drawn in DejaVu Serif, and the characters DejaVu Serif lacks in DejaVu Sans. Like JasperReports, the text is cut into the longest runs one family has, each drawn in the first family (in the order given) that has all of it; so the words around a missing character go to the other family with it. A character no family has stays in the first family, the primary one. Bold and italic text look at the faces of their style first. The families must be registered fonts or the built-in ones.
  • Font fallback (--font-fallback, or font_fallback(true)) does the same for every font, as if each were a font set of itself followed by the --font families, in the order given, and then DejaVu Sans, DejaVu Serif and DejaVu Sans Mono. It is off by default, because JasperReports does not do it, and texts whose characters are all in their font are drawn as without it.

Either way the text is measured, broken into lines and embedded in the PDF with the font that draws each run. A plain text drawn in more than one font is laid out like styled text, as in JasperReports, and stays plain text in Excel, Word and CSV.

Hyphenation

JasperReports does not hyphenate: a word that does not fit at the end of a line goes to the next one, and a word longer than the line is cut between letters. ferroreport does the same unless the template asks for hyphenation with its own property, ferroreport.text.hyphenate, which JasperReports ignores:

<!-- every text of the report, in the language of the render's locale (--locale) -->
<property name="ferroreport.text.hyphenate" value="true"/>

<!-- or in a language of its own; "false" turns it off -->
<property name="ferroreport.text.hyphenate" value="es"/>

In .ferro: property ferroreport.text.hyphenate value=true under report. The setting is the report's: tables, lists and subreports follow it unless they have their own, and on an element it is not read (the template loads with a warning; a text in another language can go in a subreport). It is also a parameter of the same name, so a render can turn it on without changing the template: {"ferroreport.text.hyphenate": "es"} in the parameters. A word that does not fit is cut after the last of its syllables that fits with a hyphen, and the hyphen is drawn; the rest of the word starts the next line. Only words made of letters are hyphenated, never inside numbers or codes, with at least two letters before the hyphen and two or three after it, as each language's patterns say. The height of a stretching text and where a text is cut across pages follow the hyphenated lines. Styled and HTML text, right-to-left and complex-script text are not hyphenated.

The patterns of English, Spanish, French, Italian, Portuguese and Catalan are built in (about 60 KB). Rust users who need more build with the hyphenation-all feature (the 48 languages of hypher, about 1.1 MB more), or without default features to leave hyphenation out. A language without patterns is not hyphenated.

Locale and dates

The locale decides how patterns such as #,##0.00 and dd MMMM yyyy are written: decimal and grouping separators, month and day names. Supported: en_US, es_DO, es_MX, es_ES, es_AR, es_CO, es_CL, es_PE (and the other Spanish-speaking countries), fr, fr_FR, fr_BE, fr_CA, fr_CH, fr_LU, fr_MA, fr_SN (and the other French regions), pt, pt_BR, pt_PT, it, it_IT, it_CH, de, de_DE, de_AT, de_CH.

Dates are kept as written, without time zone conversion. new Date() in an expression is the current time, unless you fix it with now, which makes the output byte-for-byte reproducible.
