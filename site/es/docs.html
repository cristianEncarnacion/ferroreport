Documentación

ferroreport toma una plantilla (el .jrxml de JasperReports, o su propio .ferro), tus filas en JSON y tus parámetros, y devuelve un PDF, un libro de Excel, un documento de Word, una presentación de PowerPoint, un archivo OpenDocument, un CSV o una vista previa en HTML. Todas las formas de llamarlo, de la línea de comandos a Python, usan el mismo motor y dan los mismos bytes.

Tu primer PDF

Necesitas tres archivos: la plantilla que diseñaste en Jaspersoft Studio, las filas y los parámetros.

ferroreport render invoice.jrxml --data rows.json --params params.json -o invoice.pdf
# rows.json: un objeto por fila de detalle; las claves son los nombres de los <field> de la plantilla
[
  { "sku": "FX-1000", "description": "Hydraulic pump 2HP", "qty": 21, "price": "185.00" },
  { "sku": "FX-1007", "description": "Stainless steel valve", "qty": 26, "price": "42.50" }
]

# params.json: una clave por cada <parameter>
{ "CUSTOMER": "Distribuidora Caribe, S.A.", "ISSUED": "2026-03-05", "TAX_RATE": "0.18" }

Lo mismo desde código:

// JavaScript
import { render } from "ferroreport";
const pdf = render(jrxml, rows, params, { locale: "es_DO" });

# Python
import ferroreport
pdf = ferroreport.render("invoice.jrxml", rows, params, locale="es_DO")

# Cualquier lenguaje, por HTTP
curl -X POST localhost:8080/render/invoice -H 'Content-Type: application/json' \
  -d '{"data": [...], "params": {...}, "locale": "es_DO"}' -o invoice.pdf

Plantilla, datos y parámetros

Plantilla

El código fuente JRXML, tal como lo guarda Jaspersoft Studio (JRXML 6, y JRXML 7 como lo escribe JasperReports 7), o una plantilla .ferro: toda función que recibe una plantilla acepta cualquiera de las dos. Los archivos .jasper compilados nunca se cargan: si una plantilla nombra lines.jasper, ferroreport lee lines.jrxml (o lines.ferro) en su lugar.

Datos

Un arreglo JSON con un objeto por fila, o un objeto JSON por línea (JSON Lines). Las claves coinciden con los <field name="...">; un campo llamado customer.name lee {"customer": {"name": ...}}. Una clave que falta o un null dan un campo nulo. Cada valor se convierte a la clase que declara el campo:

Clase del campoEl JSON que envías
StringUn texto (los demás valores se escriben como texto)
Integer, Long, Double, FloatUn número, o un texto con un número
BigDecimalUn número o un texto. Usa un texto como "185.00" para conservar los dígitos exactos
Booleantrue / false, o "true"
Date, Timestamp, TimeTexto ISO-8601 ("2026-03-05", "2026-03-05T10:30:00", con o sin zona horaria) o milisegundos desde 1970 (epoch)
byte[] (imágenes)Texto en base64 o un URI data:
List, CollectionUn arreglo anidado, por lo general las filas de un subreporte

Los reportes sin fuente de datos pueden omitir los datos. La consulta SQL de una plantilla se ejecuta en la base de datos que indicas con --db (ver Filas desde una base de datos); sin ella, envía las filas.

Las filas de las librerías con las que lees los datos entran como vienen, o con una llamada que las vuelve valores simples:

# pandas: pasa el DataFrame como texto JSON. to_json escribe NaN como null y las fechas en
# ISO-8601; to_dict("records") dejaría NaN, que no es JSON válido.
pdf = ferroreport.render("orders.jrxml", df.to_json(orient="records", date_format="iso"))

# Polars: to_dicts() da valores de Python (None para nulos, datetime.date para fechas)
pdf = ferroreport.render("orders.jrxml", df.to_dicts())

# SQLAlchemy: filas como dicts; un generador se lee fila por fila
from sqlalchemy import text

with engine.connect() as conn:
    result = conn.execute(text("select id, customer, placed, total from orders order by id"))
    pdf = ferroreport.render("orders.jrxml", (dict(row) for row in result.mappings()))

Parámetros

Un objeto JSON con una clave por cada <parameter>, convertidos con las mismas reglas. Los parámetros que no envías toman su defaultValueExpression.

Plantillas en .ferro

.ferro es el formato de plantilla propio de ferroreport: los mismos reportes que en JRXML, escritos como un esquema con sangría en vez de XML. Ocupa más o menos la mitad, una persona lo puede escribir sin diseñador, y sus reportes son accesibles por defecto.

  field salary Double
  variable total Double calculation=Sum : {salary}

    h1 0,0 555x30 size=18 : Employees
  columnHeader 20
    text 0,0 300x20 bold : Name
    text 300,0 255x20 bold align=right : Salary

Textos y campos

Un text se imprime tal como está escrito, salvo que tenga huecos: {nombre} (un campo), $P{nombre}, $V{nombre} o $R{clave} se llenan con los datos.

EscribesY obtienes
text : OverdueEl texto, tal cual. Las llaves que no encierran un nombre también se quedan: {0}, {a b}
text : Invoice {number} · {customer}El texto con los valores dentro
text pattern=#,##0.00 : {total}El valor solo, como un número (o una fecha) que pattern= formatea
text : ={qty} * {price}Un texto que empieza con = es una expresión, como en una hoja de cálculo
text : \{not a hole\} costs \$5\{, \}, \$, \= y \\ imprimen el carácter mismo

Los campos no necesitan declararse. Un campo escrito como {nombre} que no tiene una línea field se declara solo, en el reporte o en el each donde se usa, con la clase Object: sus valores conservan el tipo que les dan los datos (texto, número, verdadero o falso, una lista). Declara un campo para darle una clase: las fechas, que llegan como texto, necesitan field due Date para que pattern= las pueda formatear, y JasperReports necesita la clase de un campo que se usa en cuentas o en una condición para compilar el JRXML. $F{nombre} sí necesita su declaración.

Accesible por defecto. Un reporte .ferro da un PDF etiquetado, el que siguen los lectores de pantalla, salvo que diga tagged=false, en el idioma de lang= (o del locale). h1 a h6 son títulos (un texto estático etiquetado como tal), alt="..." describe una imagen y tag=th (o td, table, h2...) dice qué es cualquier elemento.

Sin coordenadas

La posición y el tamaño se pueden omitir, y ferroreport los calcula:

report "Employees" lang=en
  field salary Double

  def money value
    text pattern=#,##0.00 align=right : {{value}}

  title gap=6
    h1 height=30 size=18 : Employees
    text height=14 color=gray : Everyone on the payroll
  detail
    row height=16
      text 3fr : {name}
      use money 1fr value={salary}
EscribesY obtienes
Partes sin x,yUna debajo de otra, del ancho de la banda (o del frame); la banda es tan alta como hace falta, salvo que dé una altura
rowSus partes una al lado de otra. Cada una dice su ancho: en puntos (100), un porcentaje de la fila (40%) o una fracción de lo que queda (2fr, 1fr; una parte sin ancho es 1fr). height= fija la altura de sus partes
stackPartes una debajo de otra dentro de una fila
gap=En una banda, frame, fila o stack: el espacio entre sus partes, en puntos (4 si no dices nada)
def nombre parámetros...Una definición: las partes de abajo, con {{parámetro}} donde va un valor
use nombre parámetro=valorLas partes de la definición, con los valores puestos. Un ancho (1fr) y los demás atributos de use van a sus partes
if : {overdue}Sus partes se imprimen solo cuando se cumple la condición, y si no, no ocupan espacio (un frame con printWhenExpression y removeLineWhenBlank)
each : {lines}Sus partes se repiten por cada fila de una lista anidada; las líneas field de adentro declaran los campos de esas filas, cuando necesitan una clase (un componente lista sobre un subdataset)
import "parts.ferro"Las definiciones, estilos y campos de otro archivo, de la carpeta de la plantilla o de las carpetas de recursos

Una parte colocada así flota (baja cuando la de arriba crece) y un campo de texto crece con su texto, así que nada se encima cuando un valor es más largo de lo esperado. Las partes que dan x,y se quedan donde dicen. convert escribe el resultado como JRXML con todas las coordenadas calculadas, que Jaspersoft Studio y JasperReports abren como cualquier otro reporte.

Todo lo que dice un JRXML 7 se puede decir en .ferro, así que convertir de uno a otro no pierde nada:

ferroreport convert invoice.jrxml -o invoice.ferro      # JRXML 6 o 7 -> .ferro
ferroreport convert invoice.ferro -o invoice.jrxml      # .ferro -> JRXML 7, para Jaspersoft Studio 7
ferroreport convert old.jrxml --to jrxml -o new.jrxml   # JRXML 6 -> JRXML 7

Desde código: convert(template, "ferro") en JavaScript, ferroreport.convert(template, to="ferro") en Python, ferroreport::template::from_jrxml, to_jrxml y ferroreport::convert::jrxml_to_v7 en Rust. Cada fixture sale con los mismos píxeles desde su JRXML, su JRXML 7 y su .ferro.

El diseñador

El diseñador crea y cambia plantillas en el navegador, sin escribirlas y sin saber de JasperReports: la página en el centro, los campos de tus datos a la izquierda, y cómo se ve la parte seleccionada a la derecha. Corre en tu computadora (el motor es WebAssembly), así que ni la plantilla ni los datos salen de ella, y guarda tu trabajo en el navegador hasta que empiezas un reporte nuevo. Habla español e inglés (el botón EN / ES; al principio, el idioma de tu navegador), y la primera vez que se abre muestra una guía de tres pasos, que Ayuda, Primeros pasos vuelve a mostrar.

  1. Empieza con el ejemplo de facturas, un reporte en blanco o un archivo (Archivo, Abrir un archivo…: un .ferro o un .jrxml; un .ferro que importa otros se abre cuando los seleccionas juntos, y un archivo JSON seleccionado con él pasa a ser los datos).
  2. Agrega tus datos: Subir archivo de datos, o Editar datos de ejemplo (una lista de filas en JSON). El diseñador muestra sus campos con sus tipos en palabras sencillas (texto, número, número entero, fecha, sí o no, lista).
  3. Arrastra un campo a la página, o selecciona un área y haz clic en el campo. Las áreas tienen nombres sencillos: Título del reporte (arriba de la primera página), Arriba de cada página, Títulos de columna, Cada fila de tus datos (se repite), Debajo de las filas, Abajo de cada página, Final del reporte (totales); sus nombres de JasperReports están en sus descripciones emergentes. Un área vacía es una franja delgada que dice Agrega algo aquí. Un campo que sueltas en las filas lleva un título de columna encima; los números se alinean a la derecha con un formato; una lista (un arreglo en cada fila) se vuelve una parte que se repite por cada elemento, con sus campos adentro.
  4. Selecciona una parte para cambiarla. Su cuadro Texto lleva palabras y campos como los escribe .ferro, Invoice {number} · {customer}: escribe {, o usa Insertar un campo, para elegir uno, y la página muestra cada campo como una píldora con su nombre. Un texto que se calcula con una fórmula (una llamada a un método, una cuenta, una condición) se muestra en Avanzado, como lo escribe JasperReports, y se guarda tal como estaba. Lo demás está en secciones: Aspecto (fuente, tamaño, negrita, cursiva, subrayado, colores), Alineación, Borde, y, plegadas, Posición y tamaño y Avanzado (crecer si el texto es largo, en blanco cuando no hay valor, mostrar solo cuando, la fórmula). Los formatos de número se eligen por un ejemplo (1,234.56, $1,234.56, 12%, 2026-11-24). Ctrl+Z deshace; las flechas mueven.
  5. Descargar PDF (el botón principal), o Excel, Word o PowerPoint desde su menú; la pestaña Vista previa muestra el PDF, que se vuelve a hacer un momento después de cada cambio. Archivo guarda la plantilla como .ferro o .jrxml (JasperReports 7). Cuando el reporte no se puede hacer, un mensaje sobre la página dice por qué en palabras sencillas y qué hacer, con el mensaje del propio motor en Detalles técnicos.

Las partes que todavía no puede editar (gráficos, tablas, crosstabs, subreportes, códigos de barras) se muestran como cajas y se guardan tal como estaban. Las imágenes se guardan dentro de la plantilla como URI data:, que ferroreport lee y JasperReports no: dale a JasperReports la imagen como archivo. Un .ferro que guarda tiene todas las posiciones escritas, como lo escribe convert, y los import y def quedan expandidos.

Los editores pueden hacer lo mismo desde JavaScript: toTree(template) da cualquier plantilla como un árbol de su forma JRXML 7, y fromTree(tree, "ferro" | "jrxml") la vuelve a escribir (ver JavaScript).

doctor

Muestra lo que usa una plantilla y si ferroreport la puede generar. Córrelo sobre una plantilla antes de depender de ella. Ver Revisar una plantilla.

convert

Reescribe una plantilla: JRXML (6 o 7) como .ferro, .ferro como JRXML 7, o JRXML 6 como JRXML 7, de la forma en que JasperReports 7 escribe sus propias muestras. La extensión de la salida, o --to ferro / --to jrxml, elige el formato; sin ninguna de las dos, un JRXML pasa a .ferro y un .ferro pasa a JRXML. Sin -o el resultado va a la salida estándar. Las plantillas de estilos (.jrtx) también se convierten.

migrate

Revisa cada plantilla de una carpeta y sus subcarpetas (.jrxml y .ferro) antes de que pases a ferroreport: si carga, qué usa, qué no está soportado todavía, y si se genera sin filas (las imágenes se buscan junto a cada plantilla, en su carpeta superior y en cada carpeta de --resources). Imprime una línea por plantilla y un resumen; --report migration.md (o .json) escribe el resultado de cada plantilla. Con --to ferro --out converted/ (o --to jrxml, para JRXML 7) también escribe cada plantilla convertida, en las mismas carpetas. Termina con 1 cuando una plantilla no se puede cargar, así que puede detener un build; con --strict también cuando una usa algo que todavía no está soportado, se detiene al generarla sin filas, o difiere de JasperReports. --strict-pixels (con --jasper) también lo hace fallar cuando una página de una plantilla que generan los dos motores es otra imagen, o cuando las páginas no se pudieron comparar (sin pdftoppm). Una plantilla que uno de los motores no puede generar queda para --strict.

La guía de migración lleva un proyecto de JasperReports por este proceso paso a paso.

Comparado con el propio JasperReports

Con --jasper lib/, la carpeta de tus jars de JasperReports (6 o 7, con sus dependencias, como los corre tu aplicación) y un JDK 11 o más nuevo en el PATH, cada plantilla que carga también la genera JasperReports, en un solo proceso de Java, y ferroreport, con las mismas filas: <name>.json o data.json junto a la plantilla, y los parámetros de <name>.params.json o params.json (locale en_US y zona horaria UTC en los dos). Para cada una informa las páginas de cada motor, si cada texto y número es el mismo y está en el mismo lugar (sus exportaciones a CSV, comparadas línea por línea), si cada página es la misma imagen, y cuánto tardó cada uno en llenar y escribir el PDF. Los errores vuelven como {"error": "what went wrong"} con uno de estos estados: 400 la petición está mal formada, 401 falta el token o es incorrecto, 404 la plantilla no existe, 411 la petición no tiene Content-Length y pide cambiar de protocolo, 413 el cuerpo es demasiado grande o la generación pasó el límite de páginas o de tiempo, 429 el cliente pidió demasiadas veces (--rate-limit), 422 la plantilla o sus datos no se pueden generar, 507 el documento es demasiado grande para la memoria y el disco que puede usar el servidor (--spool-memory, --spool-dir, --spool-disk).

Un documento se envía solo cuando está completo, con su Content-Length: la respuesta es el documento entero o un error, nunca una parte. Llega con dos encabezados más: Server-Timing (milisegundos usados para interpretar la plantilla, 0 cuando vino de la caché, y para generarla) y X-Report-Pages.

Toda respuesta, también las de error, lleva X-Request-Id: el que envió la petición, si es ASCII imprimible de 128 caracteres o menos, o uno nuevo. Con --access-log json (o FERROREPORT_ACCESS_LOG=json) el servidor imprime un objeto JSON por petición en la salida de errores, para Loki, CloudWatch, Datadog o ELK. Reportes grandes por HTTP

Hay dos cosas que se pueden cambiar, cada una por su lado, para reportes con más filas de las que quieres en memoria.

Filas una por línea. Envía Content-Type: application/x-ndjson con la petición (todo lo de la tabla de arriba menos data) en la primera línea, y una fila por línea después. El servidor lee las filas a medida que el reporte las pide, así que ningún lado las tiene todas: un millón de filas se generan con el servidor en unos 50 MB. Envíalas directo desde una consulta:

# rows.ndjson
{"params": {"YEAR": 2026}}
{"sku": "FX-1000", "qty": 21, "price": "185.00"}
{"sku": "FX-2000", "qty": 4, "price": "92.50"}

curl -X POST localhost:8080/render/sales -H 'Authorization: Bearer change-me' \
  -H 'Content-Type: application/x-ndjson' -T rows.ndjson -o sales.pdf

# o sin archivo, a medida que la base de datos las produce
psql -At -c "select row_to_json(s) from sales s" | { echo '{"params": {"YEAR": 2026}}'; cat; } | \
  curl -X POST localhost:8080/render/sales -H 'Authorization: Bearer change-me' \
    -H 'Content-Type: application/x-ndjson' -T - -o sales.pdf

La primera línea puede ser tan grande como --max-body; las filas no tienen límite propio (--timeout, --max-pages y --max-rows son los que detienen un reporte demasiado grande).

El documento mientras se genera. Por defecto el servidor guarda el documento hasta que está completo (en memoria hasta --spool-memory, después en un archivo), para que un error sea siempre un error y nunca medio PDF. Agrega Prefer: respond-streaming y el documento se envía mientras se genera: los primeros bytes llegan en una fracción de segundo, por largo que sea el reporte, y no se guarda nada en el servidor. La respuesta lo indica con Preference-Applied: respond-streaming.

Por defectoPrefer: respond-streaming

Después el estado ya es 200, así que la respuesta se corta de una forma que todo cliente HTTP informa como error (curl termina con 56, Java lanza IOException, Python lanza IncompleteRead). Los dos dan los mismos bytes. Usa el modo por defecto salvo que necesites los primeros bytes pronto (la descarga de un reporte largo en el navegador, un gateway con un tiempo de espera corto) o quieras que las descargas abandonadas dejen de costar trabajo. En Docker los archivos van a /tmp, que la imagen trae; con un sistema de archivos raíz de solo lectura, monta un volumen ahí o define FERROREPORT_SPOOL_DIR. Sin un lugar donde escribir, los documentos de más de --spool-memory se responden con 507.

Estas promesas se comprueban en cada cambio con tools/http_check.py: un millón de filas, 50 clientes a la vez, un cliente que se va a la mitad, una fila incorrecta en cada modo, y los mismos bytes que la línea de comandos para cada reporte de prueba.

Imágenes, subreportes y plantillas de estilos

Una plantilla nombra otros archivos por su ruta relativa: "logo.png" en la expresión de una imagen, "lines.jasper" en la expresión de un subreporte. ferroreport los busca en la carpeta de la plantilla, después en las carpetas de recursos que agregas, y después entre los recursos que pasas en memoria. Una ruta nunca puede salir de esas carpetas, y las URL remotas no se descargan.

Las imágenes son PNG, JPEG o GIF (su primera imagen, con su color transparente). También pueden venir de los datos: un campo byte[] con contenido en base64, o un campo de texto con una expresión en base64.

Un subreporte recibe sus filas de un arreglo anidado en la fila del reporte principal:

# Fila del reporte principal
{ "order": "ORD-2026000", "customer": "Grupo Ramos",
  "lines": [ { "product": "Clavos 3\"", "qty": 26, "price": 65.0 }, ... ] }

# En la plantilla principal: un campo de clase java.util.List, y
<dataSourceExpression><![CDATA[new JRMapCollectionDataSource($F{lines})]]></dataSourceExpression>
<subreportExpression><![CDATA["lines.jasper"]]></subreportExpression>    # se lee de lines.jrxml

JRBeanCollectionDataSource, ((JsonDataSource)$P{REPORT_DATA_SOURCE}).subDataSource("lines") y JREmptyDataSource funcionan igual. Se soportan los parámetros de los subreportes y los valores que devuelven.

Las plantillas de estilos se buscan igual: <template><![CDATA["styles.jrtx"]]></template> lee styles.jrtx de la carpeta de la plantilla, de una carpeta de recursos o de los recursos en memoria (por HTTP, los resources de la petición). Un .jrtx que incluye otro se lee con él, y el incluido se busca primero junto a él. Los estilos se toman en el orden de JasperReports: los de cada plantilla después de las plantillas que incluye, y después los del propio reporte; un estilo definido otra vez reemplaza al anterior para lo que viene después. La ubicación puede ser un texto o un parámetro cuyo valor por defecto sea uno. En Rust, interpreta con Renderer::parse en vez de ferroreport::parse, que no lee archivos.

Tablas

Las tablas (jr:table) funcionan como en JasperReports: la tabla recorre un <subDataset> cuyas filas vienen de la dataSourceExpression de su datasetRun, por lo general un arreglo anidado de la fila actual, y sus datasetParameter le pasan valores. Los campos del reporte principal no se ven dentro de la tabla; pásalos como parámetros.

<subDataset name="lines">
  <parameter name="ORDER" class="java.lang.String"/>
  <field name="product" class="java.lang.String"/> ...
</subDataset>
...
<jr:table>
  <datasetRun subDataset="lines">
    <datasetParameter name="ORDER"><datasetParameterExpression><![CDATA[$F{order}]]></datasetParameterExpression></datasetParameter>
    <dataSourceExpression><![CDATA[new JRMapCollectionDataSource($F{lines})]]></dataSourceExpression>
  </datasetRun>
  <jr:column width="235"> ... </jr:column>
</jr:table>

Se soportan: columnas y grupos de columnas anidados, encabezado y pie de tabla, encabezados de columna (que se vuelven a imprimir en cada página en la que sigue la tabla), pies de columna, celdas de detalle, celdas de encabezado y pie de grupo para los grupos del subdataset, printWhenExpression en las columnas, la celda sin datos (whenNoDataType="NoDataCell") y las variables del subdataset. Las filas vienen de la expresión de la fuente de datos o, cuando el dataset run pasa $P{REPORT_CONNECTION}, de la consulta SQL del subdataset en la base de datos del reporte.

Las listas (jr:list) usan el mismo datasetRun: el contenido de la lista se repite por cada fila, una debajo de otra, y sigue en la página siguiente cuando no cabe.

Crosstabs

Los crosstabs (tablas cruzadas) hechos en Jaspersoft Studio salen como en JasperReports. Las filas vienen del propio reporte (pon el crosstab en la banda summary) o de un subdataset por su datasetRun, por ejemplo un crosstab por fila de detalle sobre un arreglo JSON anidado.

  • Los grupos de filas y de columnas ordenan sus valores de forma ascendente o descendente, e imprimen sus totales al principio, al final o nunca. Los encabezados de grupo van al principio, en el medio o al final de las celdas que abarcan (headerPosition).
  • Las medidas pueden ser Sum, Count, DistinctCount, Average, Highest, Lowest, First o Nothing. En una celda, $V{measure} es el valor de esa celda, $V{measure_group_ALL} el total de un grupo, $V{measure_rowGroup_columnGroup_ALL} el total de los dos, y $V{group} el valor del grupo. Las celdas sin datos muestran cero en sumas y conteos. Los totales suman los totales de los grupos de abajo, como lo hace Jasper, así que los decimales se redondean igual.
  • Un crosstab más ancho que su elemento se corta en partes de columnas, impresas una debajo de otra (a columnBreakOffset de distancia) con los encabezados de fila repetidos. Uno más alto que la página sigue en la página siguiente con los encabezados de columna repetidos (repeatColumnHeaders, repeatRowHeaders).
  • Los valores de <crosstabParameter> se evalúan en el reporte y se leen con $P{} dentro del crosstab.
  • percentageOf="GrandTotal" muestra una medida como porcentaje del total general (100 × valor / total, en la clase de la medida: los enteros se dividen como enteros, BigDecimal redondea hacia arriba desde la mitad).
  • orderByExpression ordena los valores de un grupo por un valor calculado sobre los totales de cada uno, por ejemplo $V{amountMeasure} para listar las regiones por sus ventas; los empates mantienen el orden natural.

Todavía no: comparadores de valores (comparatorExpression), y crosstabs solo sobre las filas de un grupo (usan todas las filas leídas hasta ese momento). ferroreport doctor avisa de ambos.

Excel y CSV

Una plantilla que se genera en PDF también se exporta a un libro de Excel (.xlsx) o a un archivo CSV. Los dos siguen los exportadores del propio JasperReports con su configuración por defecto, así que la hoja de cálculo sale como salía con Jasper: cada fixture de la batería de pruebas da la misma hoja, los mismos estilos y el mismo texto CSV que JasperReports 6.20, byte por byte.

Excel

  • Todas las páginas van en una hoja con el nombre del reporte, una debajo de otra, con los márgenes de página incluidos.
  • Los bordes de los elementos cortan cada página en columnas y filas. Una columna es tan ancha como el espacio entre dos cortes (en unidades de Excel de 6 puntos) y una fila tan alta como el suyo, en puntos.
  • Cada texto ocupa las celdas que cubre, combinadas, con su fuente, tamaño, negrita, cursiva, subrayado, color, fondo, bordes y alineación. El texto rotado se rota en la celda. El texto con estilos y el HTML conservan su formato tramo por tramo.
  • Un texto que no cabe en su caja se corta igual que en el PDF.
  • Las líneas pasan a ser el borde de las celdas sobre las que están, los rectángulos rellenan y bordean sus celdas, y los frames dan su fondo y sus bordes a las celdas de adentro.
  • Las imágenes van sobre sus celdas con el mismo modo de escala (RetainShape, FillFrame, Clip) y la misma alineación. Los gráficos y los códigos de barras se dibujan como imágenes al doble de la resolución de Jasper, así que se ven nítidos.
  • Donde dos elementos se enciman, gana el de arriba, como en Jasper; el otro se deja fuera.
  • Los valores se escriben como el texto que ves en el PDF (3,885.00), igual que en Jasper. Con --xlsx-numbers en la línea de comandos, o XlsxOptions { detect_cell_type: true } en Rust, los números se escriben como números con su patrón de formato, así que la hoja de cálculo los puede sumar.

CSV

Solo se exportan los textos. Cada línea de una página donde empieza un texto pasa a ser una fila, y cada columna donde empieza un texto en esa página pasa a ser un campo. Los campos que llevan una coma, una comilla o un salto de línea van entre comillas; las comillas se duplican. Las páginas van una tras otra.

Un valor que empieza con =, +, - o @ puede ejecutarse como fórmula en la hoja de cálculo que abre el CSV. Cuando los datos vienen de otras personas, activa la protección (--csv-safe, csv_safe=True, csvSafe: true): esos valores llevan un apóstrofo delante, que las hojas de cálculo muestran como texto. Los números como -12.50 no se tocan. Está desactivada por defecto para que el CSV sea exactamente el que escribe JasperReports.

Todavía no está disponible: el formato XLS antiguo y las propiedades net.sf.jasperreports.export.* salvo la detección de números.

Word

Pide docx (-o report.docx, format="docx", Format::Docx, Format.DOCX) y obtienes un documento de Word armado como el del exportador DOCX de JasperReports: cada página es una tabla cortada en los bordes de sus elementos, y cada elemento ocupa las celdas que cubre. Los textos conservan sus fuentes, tamaños, colores, tramos con estilo, alineación, márgenes internos, bordes y fondos; las imágenes, los gráficos y los códigos de barras son imágenes; las líneas y los rectángulos pasan a ser bordes y fondos de celda. Un salto de página separa las páginas, así que el documento tiene tantas páginas como el PDF. Como el de Jasper, el documento está hecho para leer y editar un poco, no para que el texto se reacomode: los rectángulos redondeados y las elipses salen como cajas simples.

PowerPoint

Pide pptx (-o report.pptx, format="pptx", Format::Pptx, Format.PPTX) y obtienes una presentación armada como la del exportador PPTX de JasperReports: cada página es una diapositiva del tamaño de página del reporte, y cada elemento es una forma en el lugar que ocupa en la página. Los textos son cuadros de texto con sus fuentes, tamaños, negrita, cursiva, subrayado, tachado, colores, tramos con estilo, alineación, márgenes internos, fondo, interlineado y rotación; los rectángulos (también redondeados), las elipses y las líneas son formas con su relleno y su trazo; los frames son rectángulos debajo de sus elementos; las imágenes son imágenes recortadas a su elemento como en el PDF, y los gráficos y los códigos de barras se dibujan como imágenes. Una caja con el mismo borde en todos los lados lo lleva como contorno de la forma, y los bordes distintos en cada lado se dibujan como líneas (el exportador de Jasper los deja fuera). Los enlaces a páginas web y a otros archivos funcionan, y los enlaces a una página o a un ancla del reporte saltan a su diapositiva. Las diapositivas se escriben a medida que se llenan las páginas.

Todavía no está disponible: las propiedades net.sf.jasperreports.export.pptx.* (como una página usada como patrón de diapositivas) y las fuentes incrustadas en el archivo. PowerPoint y LibreOffice reparten el texto en líneas con sus propias medidas de fuente, así que una línea que apenas cabe en el PDF puede partirse en la diapositiva.

OpenDocument (ODS y ODT)

Pide ods u odt (-o report.ods, format="odt", Format::Ods, Format.ODT) y obtienes los archivos que abren LibreOffice y las demás aplicaciones OpenDocument, armados como arman un reporte los exportadores ODS y ODT de JasperReports. La hoja de cálculo es la cuadrícula de Excel: todas las páginas en una hoja, las mismas columnas, filas, celdas combinadas, fuentes, colores, bordes, alineación y rotación, las imágenes sobre sus celdas, los gráficos y códigos de barras como imágenes. Los valores son texto por defecto, como en Jasper; con --xlsx-numbers los números son números, con un estilo de número hecho de su patrón (decimales, separador de miles, porcentaje, notación científica, texto alrededor). El documento de texto es el armado de Word: una tabla por página, cada elemento en las celdas que cubre, un salto de página entre páginas; las elipses y las líneas inclinadas se dibujan como imágenes. Los enlaces, las anclas y las anclas de página se conservan, y la página tiene el tamaño del reporte.

Todavía no está disponible: las propiedades net.sf.jasperreports.export.ods.* y .odt.*, celdas de fecha para patrones con nombres de mes o de día, AM/PM, año de dos dígitos o milisegundos (quedan como texto), el signo por mil en los estilos de número, y el texto de cabeza en ODT.

Los reportes grandes se escriben a medida que se hacen, en más o menos la memoria de uno pequeño. Los estilos de un documento van antes de su contenido en el archivo, así que un reporte grande se llena una vez más antes para encontrarlos (una hoja de cálculo tres veces en total: sus columnas, sus estilos, sus filas; un texto dos), y sus filas después se comprimen y se escriben a medida que llegan: 100,000 filas en 69 MiB como ODS y 39 MiB como ODT, un millón de filas en 41 MiB como ODT. Eso necesita filas que se puedan leer otra vez, como en los libros de Excel grandes; con filas que solo se pueden leer una vez igual se obtiene el documento, que se guarda en memoria hasta que se escribe.

PDF accesibles

Un PDF es una imagen de páginas salvo que también diga qué hay en ellas. Con el etiquetado activado, el documento lleva esa descripción (un PDF etiquetado): cada elemento de texto es un párrafo y cada imagen, gráfico y código de barras una figura, en orden de lectura; las tablas y los crosstabs son tablas, con sus filas, sus celdas de datos y sus celdas de encabezado, cada encabezado diciendo si nombra una columna o una fila y cada celda cuántas columnas y filas abarca; las listas de un texto HTML son listas, cada elemento con su viñeta o su número y su contenido; las líneas, los bordes y los fondos se marcan como decoración, así que un lector de pantalla se los salta; y el documento tiene su título y el idioma del locale. Las páginas se ven exactamente igual.

PDF/A, adjuntos, firmas, cifrado, enlaces

PDF/A

Para documentos que hay que guardar por años (facturas, estados de cuenta, registros). --pdfa 2b (o 2u, 2a, 3b, 3u, 3a; pdfa en los paquetes y la API HTTP) escribe PDF/A: todas las fuentes dentro del documento, un perfil de color sRGB, la conformidad declarada en los metadatos. El nivel a además va etiquetado. Un texto en una de las fuentes estándar del PDF (una fuente que nadie provee) es un error, como en JasperReports: registra la fuente con --font. La propiedad net.sf.jasperreports.export.pdfa.conformance de la plantilla (pdfa2b...) pide lo mismo. Cada fixture se verifica con veraPDF como PDF/A-2a y PDF/A-3b en cada push.

Adjuntos

--attach invoice.xml (o invoice.xml:application/xml) lleva un archivo dentro del PDF, como las facturas electrónicas llevan su XML. PDF/A-3 acepta cualquier archivo; PDF/A-2 los rechaza. En los paquetes: attachments, una lista de rutas o de (nombre, bytes, tipo MIME).

Firmas

Enlaces y marcadores

Los campos de texto, las imágenes y los frames aceptan los hipervínculos de JasperReports: hyperlinkType Reference (una URL), LocalAnchor, LocalPage, RemoteAnchor y RemotePage, con hyperlinkReferenceExpression, hyperlinkAnchorExpression, hyperlinkPageExpression y hyperlinkTooltipExpression. anchorNameExpression le pone nombre a un lugar, y bookmarkLevel lo pone en el índice del PDF (el panel de marcadores). Funcionan en PDF (anotaciones de enlace y destinos con nombre), Excel (hipervínculos de celda y nombres definidos), Word (campos de hipervínculo y marcadores) y HTML, como los escribe JasperReports. Los enlaces javascript: y data: no se siguen en las vistas previas en HTML.

Vistas previas en HTML

Pide html (-o report.html, format="html", Format::Html, Format.HTML) y obtienes una página web con todas las páginas del reporte dibujadas como en el PDF: las mismas posiciones, fuentes, colores, imágenes, gráficos y códigos de barras. El texto es texto de verdad, así que se puede seleccionar, buscar y leer en voz alta, y todo lo que viene de la plantilla o de los datos se escapa. La página no tiene scripts y no carga nada de la red.

Cada línea de texto lleva su ancho medido, así que el diseño se mantiene incluso donde el navegador no tiene la fuente del reporte y usa otra. Úsala para mostrar un reporte en un navegador sin visor de PDF; el PDF sigue siendo el documento para imprimir o guardar. En Rust, HtmlOptions { fragment: true, .. } da solo las páginas, para ponerlas dentro de una página propia.

Lo que esto cubre, y lo que no:

  • PDF y CSV se escriben página por página. También los libros de Excel, en dos pasadas: las columnas de una hoja salen de todas las páginas, así que un reporte grande se llena una vez para encontrarlas y otra para escribir sus filas, que se comprimen y se envían a medida que se hacen (100,000 filas: unos 4.5 s y 69 MiB; 500,000: 22 s y 103 MiB). Eso necesita filas que se puedan leer dos veces: un archivo, o las filas que la línea de comandos, el servidor, Python y Java guardan aparte por ti; en Rust, render_rows_to. Los libros pequeños se siguen llenando una sola vez. Un reporte con más filas de las que caben en una hoja (1,048,576) se detiene con un error que lo dice. Los archivos OpenDocument también se escriben a medida que se hacen, llenándose una vez más antes para encontrar sus estilos (100,000 filas: 69 MiB como ODS, 39 MiB como ODT; un millón de filas como ODT: 41 MiB).
  • Los valores que se conocen después, como "página 3 de 240", un total general en el título o el total de un grupo en su encabezado, se agregan a su página cuando se conocen, sin retener la página. Si algo se dibuja encima de uno de esos valores, su página lo espera en su lugar, así que el resultado siempre es el mismo documento.
  • Un crosstab sobre las filas del propio reporte las necesita todas, así que esas filas se guardan hasta que se imprime el crosstab. Los crosstabs, tablas, listas y subreportes sobre datos anidados no se ven afectados.

Tres límites detienen un reporte que crece más de lo esperado. Ponlos siempre que las plantillas o los datos vengan de otras personas:

El límite de filas cuenta cada fila que lee la generación: las del propio reporte y las de sus subreportes, tablas, listas, gráficos y crosstabs, cada una una vez. Detiene en la primera fila de más un reporte que lee muchas filas pero imprime pocas páginas (un resumen de totales, un gráfico sobre muchos datos), que el límite de páginas no detiene.

Una generación que se pasa se detiene con un error (413 desde el servidor) y no deja ningún archivo.

Filas desde una base de datos

La consulta SQL de la plantilla se ejecuta como la ejecuta JasperReports por JDBC: los valores de $P{} van como parámetros, $P!{} se pega en el texto del SQL, y $X{IN, column, PARAM} (con NOTIN, EQUAL, NOTEQUAL, LESS, LESS], GREATER, [GREATER y las formas BETWEEN) se convierte en su condición. Los subreportes, tablas, listas, crosstabs y gráficos que pasan $P{REPORT_CONNECTION} hacen su propia consulta en la misma base. Las filas se leen a medida que el reporte las necesita.

ferroreport render sales.jrxml --db postgres://reports@db:5432/erp -p params.json -o sales.pdf
ferroreport render sales.jrxml --db mysql://reports@db:3306/erp -o sales.xlsx
ferroreport render sales.jrxml --db "jdbc:sqlserver://db:1433;databaseName=erp;user=reports" -o sales.pdf
ferroreport render sales.jrxml --db sqlite:app.db -o sales.pdf

  | ferroreport render sales.jrxml -d - -o sales.pdf

sqlite3 -json app.db "select * from sales order by region" | ferroreport render sales.jrxml -d - -o sales.pdf
mysql -N -B -e "select json_object('region', region, 'amount', amount) from sales" mydb \
  | ferroreport render sales.jrxml -d - -o sales.pdf
// Java: el ResultSet se lee a medida que el reporte lo necesita

Fuentes

DejaVu Sans, DejaVu Serif y DejaVu Sans Mono vienen incluidas. Son las familias de la extensión jasperreports-fonts, así que las plantillas que las usan coinciden exactamente con JasperReports. Una familia que el motor no tiene se reemplaza por una de las incluidas.

Agrega tus propias fuentes TrueType u OpenType con --font en la línea de comandos o register_font en Rust. Los paquetes de JavaScript y Python usan por ahora las familias incluidas.

Una extensión de fuentes de JasperReports se lee donde JasperReports la encontraría en su class path: en una carpeta de recursos (la de la plantilla o una dada con -r) con un jasperreports_extension.properties en su raíz. render y check registran las familias y los conjuntos de fuentes de los fonts.xml que nombra (net.sf.jasperreports.extension.simple.font.families.*), con los archivos de fuente en las rutas que da la extensión, y avisan de los que no pueden leer; en Rust, load_font_extensions lo hace con los recursos del renderer. Las extensiones dentro de jars no se leen: descomprime el jar en una carpeta.

El texto en negrita o cursiva de una familia que no tiene cara para ese estilo se dibuja con su cara normal, y el PDF simula el estilo como lo hace JasperReports: la negrita trazando también los contornos, la cursiva inclinando el texto.

Un carácter que la fuente del texto no tiene se deja fuera del PDF, como lo deja fuera JasperReports (cuando se mide el texto para calcular su altura igual cuenta tan ancho como la caja de glifo faltante de la fuente, como en JasperReports). Para dibujarlo con otra fuente, usa un conjunto de fuentes o las fuentes de reemplazo:

  • Los conjuntos de fuentes funcionan como el <fontSet> de una extensión de fuentes de JasperReports. Con --font-set "Serif Fallback=DejaVu Serif,DejaVu Sans" (o register_font_set), un texto cuyo nombre de fuente es Serif Fallback se dibuja en DejaVu Serif, y los caracteres que le faltan a DejaVu Serif, en DejaVu Sans. Como en JasperReports, el texto se corta en los tramos más largos que tiene una familia, cada uno dibujado con la primera familia (en el orden dado) que lo tiene completo; así que las palabras alrededor de un carácter faltante van con él a la otra familia. Un carácter que ninguna familia tiene se queda en la primera familia, la principal. El texto en negrita y en cursiva busca primero en las caras de su estilo. Las familias tienen que ser fuentes registradas o las incluidas.
  • Las fuentes de reemplazo (--font-fallback, o font_fallback(true)) hacen lo mismo con todas las fuentes, como si cada una fuera un conjunto de sí misma seguida de las familias de --font, en el orden dado, y después DejaVu Sans, DejaVu Serif y DejaVu Sans Mono. Están desactivadas por defecto, porque JasperReports no lo hace, y los textos cuyos caracteres están todos en su fuente se dibujan igual que sin ellas.

De cualquiera de las dos formas, el texto se mide, se reparte en líneas y se incrusta en el PDF con la fuente que dibuja cada tramo. Un texto simple dibujado con más de una fuente se arma como el texto con estilos, como en JasperReports, y sigue siendo texto simple en Excel, Word y CSV.

Separación en sílabas

JasperReports no separa en sílabas: una palabra que no cabe al final de una línea pasa a la siguiente, y una palabra más larga que la línea se corta entre letras. ferroreport hace lo mismo salvo que la plantilla pida separar en sílabas con su propia propiedad, ferroreport.text.hyphenate, que JasperReports ignora:

<!-- todos los textos del reporte, en el idioma del locale con que se genera (--locale) -->
<property name="ferroreport.text.hyphenate" value="true"/>

<!-- o en un idioma propio; "false" la desactiva -->
<property name="ferroreport.text.hyphenate" value="es"/>

En .ferro: property ferroreport.text.hyphenate value=true debajo de report. El ajuste es del reporte: las tablas, listas y subreportes lo siguen salvo que tengan el suyo, y en un elemento no se lee (la plantilla carga con una advertencia; un texto en otro idioma puede ir en un subreporte). También es un parámetro con el mismo nombre, así que una generación puede activarlo sin cambiar la plantilla: {"ferroreport.text.hyphenate": "es"} en los parámetros. Una palabra que no cabe se corta después de la última de sus sílabas que cabe con un guion, y el guion se dibuja; el resto de la palabra empieza la línea siguiente. Solo se separan las palabras hechas de letras, nunca dentro de números o códigos, con al menos dos letras antes del guion y dos o tres después, según los patrones de cada idioma. La altura de un texto que crece y el lugar donde un texto se corta entre páginas siguen las líneas con guiones. El texto con estilos y el HTML, el de derecha a izquierda y el de escrituras complejas no se separan en sílabas.

Los patrones de inglés, español, francés, italiano, portugués y catalán vienen incluidos (unos 60 KB). Quien usa Rust y necesita más compila con la feature hyphenation-all (los 48 idiomas de hypher, unos 1.1 MB más), o sin las features por defecto para dejar fuera la separación en sílabas. Un idioma sin patrones no se separa en sílabas.

Locale y fechas

El locale decide cómo se escriben patrones como #,##0.00 y dd MMMM yyyy: los separadores decimales y de miles, los nombres de los meses y de los días. Soportados: en_US, es_DO, es_MX, es_ES, es_AR, es_CO, es_CL, es_PE (y los otros países hispanohablantes), fr, fr_FR, fr_BE, fr_CA, fr_CH, fr_LU, fr_MA, fr_SN (y las otras regiones francesas), pt, pt_BR, pt_PT, it, it_IT, it_CH, de, de_DE, de_AT, de_CH.

Las fechas se conservan tal como están escritas, sin conversión de zona horaria. new Date() en una expresión es la hora actual, salvo que la fijes con now, lo que hace que la salida sea igual byte por byte cada vez.
