Migrating from JasperReports

ferroreport reads the JRXML templates you already have (JasperReports 6 and 7), so a migration is not a rewrite: the templates stay as they are, Jaspersoft Studio keeps working for them, and what changes is the code that fills and exports them. This guide goes from a JasperReports project to the same reports rendered by ferroreport, one step at a time.

Before you start

  • Keep the .jrxml sources. ferroreport never loads compiled .jasper files (what to do if you only have those).
  • Put a sample of rows next to each template, as JSON: invoice.json beside invoice.jrxml, or one data.json per folder (an array of objects whose keys are the template's <field> names), and its parameters in invoice.params.json or params.json. Step 1 compares the two engines with those rows.
  • Have the folder of your JasperReports jars at hand (the lib/ of your build, with your own jars if templates call your classes) and a JDK 11 or newer on the PATH.
  • Install the command line: a binary from GitHub Releases, cargo install ferroreport-cli, or the Docker image. Every package uses the same engine.

1. Check your templates

ferroreport migrate reports/ --jasper lib/ --report migration.md

migrate looks at every .jrxml and .ferro file in the folder and its subfolders (hidden folders, node_modules and target are skipped) and reports, for each template:

  • its format: JRXML 6, JRXML 7 or .ferro;
  • whether it loads, and if not, why;
  • each thing it uses that is not supported yet, in a sentence (for example scriptletClass (a Java scriptlet) is not run: expressions that call it fail);
  • whether it renders with no rows (pictures are looked for next to the template, in its parent folder and in every --resources folder);
  • a verdict: supported; supported; its rows come from you (its query is HQL, XPath, MDX or another language that is not SQL, which ferroreport does not run); partly supported; or cannot be loaded.

With --jasper lib/, every template that loads is also rendered by JasperReports (the jars of that folder, run with the machine's java) and by ferroreport, from the same rows (<name>.json or data.json) and parameters (<name>.params.json or params.json), and the two are compared: the number of pages, every text and number in its place (their CSV exports, line by line), every page's pixels (with pdftoppm on the PATH, as tools/compare.py does; the worst page's share of differing ink is given), and the time each took. --keep compared/ keeps both PDFs and both CSVs of every template, and the diff picture of each page that differs, to look at side by side. Nothing is written next to your templates.

This is what it printed for a folder of three templates: an invoice with its rows, the same invoice with a scriptlet, and a list whose query is HQL (times left out; JasperReports could not render the second because the scriptlet's class was not among its jars):

report written to migration.md
  • --report migration.md writes a table with every template's result; --report migration.json writes the same as JSON, with the elements each template uses.
  • --strict makes the command fail when a template uses something not supported yet, stops when rendered with no rows, or differs from JasperReports; without it, only a template that cannot be loaded fails it. Use it in CI once the folder passes.
  • --strict-pixels (with --jasper) also fails it when a page looks different from JasperReports' (over 0.15% of its ink, as compared pixel by pixel), or when the pages could not be compared because pdftoppm is not on the PATH. Add it when your templates already match pixel for pixel and you want CI to keep it so.
  • --to ferro --out converted/ (or --to jrxml) also writes every template converted, in the same folders. You don't need this to migrate: ferroreport renders JRXML as it is.
  • For a single template, ferroreport doctor invoice.jrxml lists what it uses and whether each part is supported.

With no rows, detail bands never run, and a template that prints nothing when it has no data (JasperReports' default) gives no pages at all. A detail band that calls a Java class of your own shows up only when the template is rendered with rows, as an error such as unsupported static method Util.pretty(). Give every template its rows before you trust a clean result.

2. Scriptlets, your own Java classes, .jasper files

ferroreport interprets expressions from a fixed list of operations and never runs Java code. That is what makes it safe with templates from other people, and it means three things need a decision.

Scriptlets

A scriptletClass or <scriptlet> is not run, and expressions that call it fail. Move what it computes to where ferroreport can do it: a report variable (Sum, Count, DistinctCount, Average, Lowest, Highest, First, StandardDeviation, Variance, reset by report, page, column or group), an expression, or a value your code computes and passes as a field or parameter.

Java classes in expressions

Expressions can use literals, $F{}, $P{}, $V{}, Java arithmetic, common String, Number, BigDecimal, Date and List methods, Math, String.format, new DecimalFormat(..).format(..), new SimpleDateFormat(..).format(..), msg(), $R{} and JasperReports' function library (IF, SUM, DATEFORMAT, WORKDAY and the rest: 78 functions), plus a Groovy subset with closures. Static methods of your own classes are not available: rewrite the expression with the above, or compute the value in your code and pass it in. The compatibility table lists everything. A connection built in Java (DriverManager.getConnection(...) in an expression) is not either: pass $P{REPORT_CONNECTION} (step 4).

.jasper files

Compiled .jasper files are never loaded. A subreport expression that names lines.jasper keeps working: it is rendered from lines.jrxml (or lines.ferro) next to the template or in a resource folder. The compile step of your build can go.

3. Replace the Java call

Add the library from Maven Central. It has no dependencies, needs Java 11 or newer, and does not need JasperReports on the classpath:

<dependency>
  <groupId>io.github.cristianencarnacion</groupId>
  <artifactId>ferroreport</artifactId>
  <version>1.3.0</version>
</dependency>

A typical JasperReports call compiles the JRXML, fills it from a data source and exports it:

// JasperReports
JasperReport report = JasperCompileManager.compileReport("reports/sales.jrxml");
Map<String, Object> params = new HashMap<>();
params.put("REGION", "North");
JasperPrint print = JasperFillManager.fillReport(report, params, new JRResultSetDataSource(resultSet));
JasperExportManager.exportReportToPdfFile(print, "sales.pdf");

With ferroreport there is no compile step and no intermediate print: the rows are read from the ResultSet as the report needs them and pages are written as they are finished.

// ferroreport
Ferroreport reports = Ferroreport.local();   // immutable and thread-safe: keep one
reports.template(Path.of("reports/sales.jrxml"))
    .rows(resultSet)
    .param("REGION", "North")
    .locale("es_DO")
    .renderTo(Path.of("sales.pdf"));          // .xlsx, .docx, .pptx, .ods, .odt, .csv, .html: by the extension
  • .render() returns the bytes; .renderTo(OutputStream) writes to an HTTP response as the document is made; .format(Format.XLSX) picks the format when there is no file name.
  • .param(name, value) and .params(Map) take the parameters. BigDecimal keeps every digit; LocalDate, LocalDateTime, java.util.Date and java.sql dates become dates; and byte[] becomes an image. REPORT_LOCALE becomes .locale("es_DO"): number and date formats follow en_US, Spanish (es, es_ES, es_DO, es_MX, es_AR, es_CO, es_CL, es_PE and the other Spanish-speaking countries), French (fr, fr_FR, fr_BE, fr_CA, fr_CH, fr_LU, fr_MA, fr_SN and the other French regions), Portuguese (pt, pt_BR, pt_PT), Italian (it, it_IT, it_CH) and German (de, de_DE, de_AT, de_CH) for now.
  • .maxPages(n), .maxRows(n) and .timeout(Duration) stop a report that grows past what you expect.
  • Ferroreport.local() runs the native engine as a child process for each report: the one named by -Dferroreport.bin or FERROREPORT_BIN, else ferroreport on the PATH, else a copy downloaded once from the GitHub release of the library's version and checked against its SHA-256 list. In a container, copy the engine into the image and turn the download off (-Dferroreport.download=false): 
    COPY --from=ghcr.io/cristianencarnacion/ferroreport /ferroreport /usr/local/bin/ferroreport
  • Or run ferroreport serve next to your application and use Ferroreport.server(URI.create("http://reports:8080"), token): the same calls, over HTTP, with the rows sent one per line.
  • Fonts: DejaVu Sans, Serif and Sans Mono (the jasperreports-fonts families) are built in. Other TrueType or OpenType fonts are added with --font on the command line or register_font in Rust; the JavaScript, Python and Java packages use the built-in families. Font extension jars are not read.

The whole API, with Quarkus and Spring examples, is in the Java library's README. From other languages, the documentation has the same steps for the command line, HTTP, JavaScript, Python and Rust.

Exporter properties (net.sf.jasperreports.export.*) are not read yet, apart from number detection and the PDF ones for tagging, PDF/A, encryption and form fields. The Excel and CSV exports of the test templates are compared cell by cell with Jasper's (how output is verified).

6. Run both engines side by side

  1. Keep the JasperReports dependency while you switch. Route one report at a time to ferroreport (a flag per report is enough), starting with those migrate marks supported and the same pages and text.
  2. Save real rows for the reports you move, next to their templates, and run ferroreport migrate reports/ --jasper lib/ --keep compared/ again: it compares pages, texts, numbers and time with those rows, and keeps both PDFs to look at.
  3. Add ferroreport migrate reports/ --jasper lib/ --strict to CI, so that a template edited in Jaspersoft Studio that stops rendering the same is caught before it ships.
  4. Remove JasperReports when the last report has moved, and the .jasper compile step with it.

When the two engines disagree on a template, that is a bug of ferroreport. A JRXML with sample rows that renders differently is the most useful issue you can open: it becomes a new test template.

FAQ

Does it work from Java without a separate process?

There is nothing separate to install, deploy or keep running: no JNI, no JasperReports, no service of your own. You add one Maven dependency (io.github.cristianencarnacion:ferroreport) and call it from your code. The rendering itself does happen outside the JVM: Ferroreport.local() starts the native engine as a short-lived child process for each report and streams the rows to it; the engine is found on the machine or downloaded once and checked. If your platform does not allow starting processes, run ferroreport serve (a Docker image is published) and use Ferroreport.server(...) instead.

Do I need the .jrxml?

Yes, or a .ferro template. ferroreport reads the template's source and never loads compiled .jasper files. If a project only kept the .jasper files, JasperReports itself writes them back as JRXML, with the version that compiled them: JRXmlWriter.writeReport(JRLoader.loadObjectFromFile("report.jasper"), "report.jrxml", "UTF-8"). (For a test invoice compiled by JasperReports 6.20.6 and by 7.1.1, the JRXML written back rendered the same pages as the original.)

What about scriptlets?

They are not run, and neither is any other Java code of yours. ferroreport doctor and ferroreport migrate name every template that has one. Move the logic to variables, expressions or the rows you pass (step 2).

Does SQL work in subreports and subdatasets?

Yes. The report's own query, the queries of its subreports, and the queries of the subdatasets of tables, lists, crosstabs and charts that pass $P{REPORT_CONNECTION} all run on the same database, with $P{}, $P!{} and $X{} handled as JasperReports handles them. The database is given with --db (command line), serve --db (HTTP server, also for Java's Ferroreport.server(...)) or Renderer::connection (Rust). The drivers are PostgreSQL, MySQL and MariaDB, SQL Server and SQLite. Queries in HQL, XPath, MDX or other languages are not run.

Which outputs?

PDF, Excel (XLSX), Word (DOCX), PowerPoint (PPTX), OpenDocument (ODS and ODT), CSV and HTML, from every package, the command line and the HTTP server. Not XLS, RTF, XML or plain text.

Which JasperReports versions?

JRXML as JasperReports 6 and 7 write it. Every test template is compared with JasperReports 6.20.6, JasperReports' own samples with 6.20.6 and 7.1.1, and charts are drawn as JasperReports 7.1 draws them. ferroreport convert old.jrxml --to jrxml -o new.jrxml turns a JRXML 6 template into JRXML 7, if you move Jaspersoft Studio to 7 too. For templates written by older versions, run ferroreport migrate: it says whether each one loads.
