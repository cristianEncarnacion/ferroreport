ferroreport and the alternatives

ferroreport is a report engine: rows in, documents out, many of them, the same every time. It reads JasperReports' JRXML templates without a JVM and writes PDF, Excel, Word, PowerPoint, OpenDocument, CSV and HTML. The tools below are the ones it is usually weighed against. They do different jobs, so the right one depends on what you make; this page says where each fits, including where ferroreport does not. What it says of the other projects comes from their own sites and repositories, listed under Sources (read in November 2026). Speed is given only for ferroreport against JasperReports, as measured in the README; the others were not measured.

JasperReports

The Java reporting library ferroreport follows, under LGPL-3.0: JRXML templates designed in Jaspersoft Studio, compiled and filled from a data source, with exporters for PDF, HTML, Excel, Word, PowerPoint, OpenDocument, RTF, CSV, XML and text. It has a long record in production, a large community, and Jaspersoft Studio and Server around it.

Against it, ferroreport renders the same templates without a JVM and gives the same pages, pixel for pixel, on every comparable test template of its repository. The README measures it about 200 times faster from a cold start (a 2-page invoice: 2.90 s and 195 MiB for JasperReports 6.20.6, 11 ms and 18 MiB for ferroreport) and 3 to 5 times faster than a warm JVM (that invoice: 9.0 ms against 2.8 ms), and a million rows in 17.91 s and 18 MiB against 79.77 s and 1,731 MiB. Templates cannot run code: expressions come from a fixed list and nothing is deserialized. It does not run scriptlets or Java classes of your own, load .jasper files, or write XLS, RTF, XML or text, and it has no report server. The migration guide covers moving a project.

OpenPDF

A Java library for PDF files, under MPL-2.0 or LGPL-2.1 (or later): its core is a fork of iText made in 2016, before iText's license changed, and its openpdf-html module, a fork of Flying Saucer under LGPL-2.1 only, renders HTML and CSS. You build the document in code (paragraphs, tables, images, fonts) or as HTML. Since the 2.1 branch it needs Java 21. The JasperReports 6.20.6 and 7.1.1 distributions write their PDFs with a Jaspersoft build of OpenPDF.

Pick it to build PDFs from Java code. Pick ferroreport when the documents are reports (bands, groups, totals, "page X of Y", crosstabs, charts) that someone designs rather than codes, when you need Excel or Word from the same template, or when you already have JRXML.

OpenHTMLtoPDF with Thymeleaf

OpenHTMLtoPDF renders well-formed XHTML (and some HTML5) with CSS 2.1 to PDF or images, in Java, under LGPL-2.1 or later. Flexbox and grid layouts are not supported. The original repository's last release is 1.0.10 (September 2021); a community fork goes on from it (1.1.8, April 2024). It is often paired with Thymeleaf (Apache-2.0), a Java template engine, to put the data in the page.

Pick it when your team writes HTML and CSS and the documents are page-like (letters, receipts, simple invoices). Pick ferroreport for reports whose pages depend on the data: groups that start a new page, headers repeated on every page, running and page totals, values known only at the end of the report, crosstabs and charts, which in HTML you program yourself; and when you want spreadsheets or Word from the same template.

iText 8

A PDF library for Java and .NET (C#) that creates PDFs and manipulates existing ones (splitting, merging, filling forms), under AGPL-3.0 or a commercial license; under the AGPL, software built with it must be released under the same terms. Its pdfHTML add-on, under the same dual license, converts HTML and CSS to PDF and PDF/A. iText Core 9 is now the current major version, with the same licensing.

Pick it for PDF manipulation (forms, editing, merging) with a commercial license, or in an AGPL project. Pick ferroreport to generate reports from templates under MIT or Apache-2.0, with PDF/A, PDF/UA, encryption and signatures in the open-source engine, and other formats besides PDF.

Typst

A typesetting system written in Rust, under Apache-2.0: documents are written in Typst's markup, which has a scripting language built in, and compiled to PDF, PNG or SVG; HTML export is experimental, behind a feature flag, and not meant for production yet. Its company was founded in Berlin in 2023, and it has a community and a package ecosystem (Typst Universe). It sets text better than a report engine does (paragraph layout, hyphenation, math).

Pick it for documents written by people: papers, books, letters, technical documents. Pick ferroreport for data reports (bands, groups, variables, late values, a million rows streamed in flat memory), for spreadsheets and Word documents, and to reuse JRXML. In Typst you would program the report logic yourself.

Carbone

A report generator for Node.js whose templates are office documents (DOCX, ODT, XLSX, ODS, PPTX...) made in Word or LibreOffice, with tags such as {d.companyName} where the JSON data goes. It writes PDF, DOCX, XLSX, ODT, PPTX, ODS, XML and CSV; PDF and conversion to another format go through a converter (LibreOffice; version 5 can also use Chrome or OnlyOffice). The Community Edition is source-available under the Carbone Community License, which does not allow offering it to others as a hosted document-generation service, and it is one major version behind the paid Enterprise Edition.

Pick it when business users design the templates in Word or LibreOffice. Pick ferroreport when templates come from Jaspersoft Studio or are written as text, when you want an OSI license (MIT or Apache-2.0), PDF without an office suite installed, or the band and group model of JasperReports.

Apache POI and FastExcel, for spreadsheets

Apache POI (Apache-2.0) is the Java library for Microsoft Office formats: it reads and writes XLS and XLSX, writes very large XLSX files with its streaming SXSSF API, and reads and writes Word and PowerPoint files with less coverage. FastExcel (Apache-2.0) is a Java library that writes XLSX with a small memory footprint and basic styles, no charts yet, and reads the cell content of XLSX files. Both build the workbook in code, cell by cell.

Pick them for spreadsheets that are data more than layout, or to read and change existing workbooks. Pick ferroreport when the spreadsheet is a report: the same template gives the PDF and the workbook, laid out like JasperReports' exporter (merged cells, fonts, borders, images, charts as pictures) and written as it is made. ferroreport does not read workbooks and does not write XLS.

Where ferroreport is weaker

  • Maturity. Its first stable release, 1.0.0, came out in November 2026, and the current one is 1.4.0. JasperReports, iText, Apache POI and OpenPDF have far longer records in production.
  • Community. Much smaller than JasperReports', iText's, Apache POI's or Typst's: fewer people to answer questions, fewer articles, fewer integrations.
  • Custom Java components. It never runs Java code: no scriptlets, no static methods of your own in expressions, no custom components, maps, chart customizers or chart themes, no font extension jars. Templates that depend on them need changes (how).
  • Tooling. No report server, viewers or dashboards, and its browser designer is a first version (fields, text, shapes, images, styles; not yet charts, tables or groups). Jaspersoft Studio still works for its templates.
  • Coverage. No XLS, RTF, XML or text output; number and date formats for en_US, Spanish, French, Portuguese, Italian and German only; SQL queries only (no HQL, XPath, MDX), on PostgreSQL, MySQL and MariaDB, SQL Server and SQLite; it does not read or edit existing PDFs or workbooks.

What is supported and what is not yet is listed in the compatibility table, and ferroreport doctor gives the answer for one template.
